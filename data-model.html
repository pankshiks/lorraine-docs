DeYoe Wellness Acupuncture — build design

Packet tool data model

How patients, authorizations, visits and sent faxes are stored; how the forms are defined as configuration; and how every value on every page is filled — so the name, numbers and dates can't drift between documents.

Revision 10 · 23 Sep 2026Pairs with the screen spec and current-process map

What changed in this revision

  • 1
    Forms are defined as configurationOne master form definition lists every section and option in order. Each diagnosis has a small configuration saying which options it shows, which are ticked by default, and where each value prints on its scan. The entry screen is built from this, per diagnosis.
  • 2
    The patient's answers are recorded per visitType of pain, painful activities and daily-life interference are stored per visit, each visit starting from the previous visit's answers. The first visit of a new authorization for the same patient and the same diagnosis starts from that patient's last recorded visit; otherwise from the diagnosis defaults.
  • 3
    Three separate files per faxCover sheet, clinical notes and RFS are always separate PDFs, as the VA requires. The notes file is named from the patient's details.
  • 4
    The cover sheet belongs to each sendNotes and RFS belong to the packet; each destination gets its own cover sheet. This is what makes the automatic Atlanta copy of every Blairsville send possible.
  • 5
    Confirmed practice decisions built inLorraine prepares and approves · office Mac · SRFax · 20 diagnoses · no left/right printed · post-treatment always 1/10 · Excellent on the last page.
  • 6
    Only the last four of the SSNThe full Social Security number is not stored. Every document uses only the last four.
  • 8
    Visits held to the authorizationThe number of visits can't exceed what the VA approved, and visit dates must fall inside the approved period — enforced by the database, not only the screen. The last page follows the visit marked final.
  • 9
    Diagnosis settings kept as filesEach diagnosis is a folder with its scan and settings file, added by our team and loaded into the database on start-up.
  • 10
    Everything is recordedThe activity log now also covers sign-ins (including failed ones), file downloads, settings changes and system events such as diagnosis updates, app updates, test faxes and backups.
  • 11
    ICD-10 codes received (rev 10, 23 Sep)Codes for all 20 diagnoses are in the diagnosis list, stored with the dot, with a description for the RFS and a “confirmed” flag. Three codes (Hip – Left, Knee – Right, Shoulder – Right) await confirmation because the code sent is for the other side; the RFS stays off for those until then.
  • 7
    Built for more clinics, run for oneEvery clinic's data is kept apart by design, and a clinic's branches are its offices. VA facilities and the standard diagnosis list are shared reference data; each clinic keeps its own contacts, cover sheets, templates and defaults. DeYoe runs as a single clinic on its own computer.

The shape

Records hold the truth and change over time. Output is frozen the moment it is sent. Configuration describes the forms and contains no patient data. Every clinic table sits inside one clinic (tenant), whose branches are its offices. Two small reference lists — VA facilities and the standard diagnoses — are shared by all clinics and hold no clinic or patient data.

Forms as configuration

The 20 progress-note templates are the same printed form with different ticks. So there is one master form definition, and each diagnosis adds only a small settings file. The entry screen, the defaults and the printed positions all come from these two — change them, and no code changes.

per

What is recorded per visit, and what stays with the diagnosis

Per visit — date, pain level, and the patient's answers: type of pain, painful activities, daily-life interference. Each visit starts from the previous visit's answers, so only changes need touching.

Per diagnosis — objective findings, pulse and tongue, assessment, prognosis, plan, treatments, point prescription and therapies stay exactly as printed on Dr. DeYoe's scan. The master form can describe them, but they are not editable in this phase.

why

Rules that keep this safe over time

Stable keys, not labels — answers are stored under numbness, not the printed word, so correcting a label never breaks data. Versions everywhere — each visit records the form version it was filled against, and each template records its scan version, so old records always read correctly. Defaults are copied, not referenced — changing a diagnosis's defaults affects new visits only.

The tables

tenant_id, created_at, created_by, updated_at and updated_by are on every table and omitted below — except the two shared lists marked ★, which have no tenant_id.

Records — patient data

patient

PHI
  • id · version optimistic locking
  • first_name, middle_initial, last_name
  • date_of_birth
  • ssn_last_four char(4) — no full SSN
  • title Mr. / Ms. / Mrs. · pronoun his / her
  • va_patient_id optional, only if the practice uses one
One row per veteran, reused for every authorization. Returning veterans are matched on last name + date of birth + last four; the tool suggests, a person confirms. Never merged automatically.

authorization

PHI
  • id, version · patient_id
  • va_auth_number belongs here, not on the patient
  • diagnosis_id · va_facility_id · office_id
  • visits_approved · period_start, period_end both required
  • status active / complete / expired
The unit of work. A new authorization brings a new VA number. Diagnosis cannot change once visits exist — a new diagnosis is a new authorization. Limits: visits can't exceed visits_approved or fall outside the period; neither can be reduced below what's recorded. Extensions are edits here, with a reason in the activity log.

visit

PHI
  • id, version · authorization_id · patient_id
  • visit_date a date, printed top and bottom
  • sequence_no · pain_level 0–10, a real column
  • form_version e.g. progress_note@3
  • answers JSON — the patient's answers
  • answer_source JSON — default · previous visit · doctor's note · changed
  • is_final set at the last approved visit, or earlier if treatment ends
  • note_override nullable
One row per visit. The date is stored once, so top and bottom can't differ. answer_source separates what the patient actually said from what was carried forward. Unique (authorization, sequence_no) with 1 ≤ sequence_no ≤ visits_approved; at most one final visit, and none after it.

Output — frozen when sent

packet

Immutable
  • id, version · authorization_id
  • kind initial · final · correction
  • supersedes_packet_id · supersede_reason
  • rfs_template_id null when no RFS
  • snapshot JSON — every value as printed
  • state · prepared_by, approved_by, approved_at
State is a constrained sequence: draft → ready → approved → sending → sent. Only a draft can be edited. Once approved, the packet and its files are frozen and reproducible for good.

packet_document

Immutable
  • id · packet_id
  • kind clinical_notes · rfs
  • file_name John Doe 1234 Acupuncture Records VA0012345678.pdf
  • pdf_path, sha256, page_count
Separate files, as the VA requires. The notes file name is built from the patient's name, last four and VA number.

packet_page

Immutable
  • id · packet_id · document_kind · page_no
  • visit_id nullable
  • overrides JSON — values changed on this page only
The only way two documents can disagree is a deliberate per-page override — which is what the consistency check looks for.

fax_transmission

Immutable
  • id · packet_id null for a test fax · kind packet · test
  • va_facility_id · to_fax_number
  • cover_template_id · cover_pdf_path · cover_file_name
  • total_pages cover + notes + RFS
  • triggered_by manual · rule
  • attempt_no · provider_message_id · status
  • last_polled_at, poll_attempts · error_text, sent_at
The cover sheet lives here, not on the packet — each destination gets its own. SRFax accepts a fax and confirms delivery later, so a background job polls until queued becomes sent.

activity_log

Immutable
  • actor_id null for system events · category record · access · export · settings · system
  • action view · create · update · approve · send · sign_in · sign_in_failed · locked · signed_out · download · settings_changed · config_loaded · update_installed · test_fax · backup
  • entity, entity_id · before, after secrets never recorded · reason
  • occurred_at · client_info browser and device
Records who looked at patient records, not only who changed them — plus every sign-in, every file downloaded, every settings change and system events such as diagnosis updates and backups. Append-only, kept inside the encrypted database, never written to plain log files.

ai_draft

No PHI
  • id · entity, entity_id
  • prompt_sent stored exactly as sent — no names or IDs
  • response · accepted · reviewed_by
Proof, not a promise, that no identifiers were sent to Grok.

Configuration — no patient data

form_definition

New
  • id · key progress_note · cover_sheet · rfs
  • version · status
  • definition JSON — sections, fields, order, rules, per visit / per template
One master definition per document type. A new version never changes visits already recorded.

document_template

Config
  • id · kind note · cover_sheet · rfs
  • diagnosis_id / va_facility_id / office_id
  • form_definition_id · form_version
  • source_pdf untouched original · clean_background ticks erased where boxes are live
  • settings JSON — hidden, defaults, print positions, cover-ups
  • version · status ready · blocked · superseded · block_reason
Loaded from a folder per diagnosis and version (scan.pdf + settings.json), checked against the schema on start-up. Replacing a scan creates a new version; packets already sent keep the one they used.

★ diagnosis

Shared
  • id, slug
  • display_name with side, for staff — Low Back Pain – Left
  • printed_wording on the page — LOW BACK PAIN
  • icd10_code with the dot — M54.50; blocks RFS only · icd10_description RFS field 14 · icd10_confirmed RFS stays off while false
  • body_area for RFS field 18
  • body_group Back · Neck · Knee · Hip… for the picker
  • post_treatment_severity always 1
Staff pick by the name with the side; the page prints the wording without it, as the practice asked. A clinic's own scan, defaults, closing note and any wording change live in its template settings.

★ va_facility

Shared
  • id · name · address
  • main_fax, main_phone
One list for every clinic. The named contact on a cover sheet (“ATTN: …”) and its fax number are the clinic's own — they sit on the clinic's cover-sheet template.

tenant · office · practice_setting

Config
  • tenant: clinic name, status
  • office: the clinic's branches — name, address, active
  • practice_setting: provider name, NPI, phone, fax 404-738-1714, email, footer, retention periods, fax account
Practice details are printed on top of the scans, never baked in — the fax number changes in one place.

destination_rule

New
  • when_facility_id Blairsville VA
  • also_send_to_id Atlanta VA
  • cover_template_id which Atlanta cover — to confirm
  • include_rfs to confirm
One approval, two faxes — confirmed as routine by the practice.

app_user · user_membership

Config
  • app_user: id, email, password_hash, full_name, is_active, last_login_at
  • user_membership: user_id, tenant_id, roles preparer · approver · administrator
Roles belong to a clinic, so one login could later work for more than one clinic. At go-live Lorraine holds all three roles in one clinic.

How every value gets filled

A

From the records — no logic

Name, date of birth, last four, title, his/her · VA number · diagnosis wording and ICD-10 · office address · VA facility and its fax · practice phone, fax, NPI · dates · page counts · the notes file name.

B

By rule

First page from visit 1, last page from the visit marked final, middle otherwise · INITIAL VISIT and Last Visit labels and notes · Excellent on the last page, Good otherwise · post-treatment 1/10 · cover-ups from the template settings · each visit's answers start from the previous visit (first visit: same patient + same diagnosis → their last recorded visit, else diagnosis defaults) and stay editable (pain level excepted — always entered) · Blairsville sends copied to Atlanta · RFS reason assembled from the standard wording plus title and surname, body area and his/her.

C

Grok — reviewed before use

Reads Dr. DeYoe's note with names and IDs removed and proposes the template and the first visit's answers (“dull and sharp … numbness” → Dull, Sharp, Numbness) · drafts the closing note. Nothing is saved until Lorraine accepts it.

Finding things later

Because answers live under stable keys, the database can answer questions like these directly — and a reporting screen or assistant can be added later without changing anything stored.

-- Which patients reported numbness in the last 6 months, and was it really reported?
SELECT p.last_name, v.visit_date
FROM   visit v JOIN patient p ON p.id = v.patient_id
WHERE  json_extract(v.answers, '$.pain_type.numbness') = 1
  AND  json_extract(v.answer_source, '$."pain_type.numbness"') != 'default'
  AND  v.visit_date >= date('now', '-6 months');

-- Average pain drop per diagnosis, first visit to last
SELECT d.display_name, AVG(first.pain_level - last.pain_level) …

When the VA extends an authorization

Open
Assumed
Same VA number, more visits or a later end date — edited on the authorization, with a reason logged. If the VA issues a new number instead, it's recorded as a new authorization.

Is the first visit's note sent separately?

Open
Assumed
Supported, off by default. An initial packet with the “Initial Visit Acupuncture Records” cover sheet; the final packet follows at the end.

RFS field 21 — the ordering provider's signature

Open
Assumed
Nothing is signed automatically. The field is required and blank on all three forms. Options: a short sign step for Dr. DeYoe on RFS only, his signature image applied with written consent, or print-and-sign.

The Atlanta copy of a Blairsville send

Open
Assumed
Atlanta VAMC — Request for Services cover sheet; RFS included in both. Page count covers all three files.

Side wording already printed on some templates

Open
Assumed
Keep what each scan prints. Hip and right-knee templates print the side (“PAIN IN LEFT HIP”), while Low Back Pain – Left is shown without it on the Jane Doe sample. printed_wording can be set either way per diagnosis.

Retention

Open
Assumed
10 years for packets, 6 years for logs, as settings. Not legal advice — to be confirmed with the practice's own advisor.
Deliberately not built now. A general form designer · editing clinical ticks per visit · patient self check-in · reports and an assistant · inbound fax · HSRM or EHR integration · a VA login · storing the full SSN. The configuration and stored answers are shaped so the first four can be added later without changing anything already recorded.
