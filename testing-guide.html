Testing guide

End-to-end test scenarios covering the full patient journey: authorization, visit tracking, packet generation and fax. Includes the seed script prompt and a reset procedure. Use fake data only.

Version 1.0 · 1 Oct 2026 Internal not for the client HIPAA fake data only — never real names, VA numbers or DOBs
01Prerequisites 02Seed script prompt 03Patient & authorization 04Visit tracking 05Packet generation 06Fax flow 07Negative / blocked cases 08Reset procedure 09Fixture reference
How to read the scenarios. Each scenario has a Positive (should succeed), Negative (should be blocked), or Boundary (edge / limit) badge. Expected outcomes are shown at the bottom of each card. Run positive cases first to confirm the happy path, then negative cases to confirm guards hold.
HIPAA reminder. Use only fictional patients (Jane Doe, John Doe). No real names, dates of birth, VA authorization numbers, or SSN digits anywhere — in the database, logs, screenshots, or commit messages. Real patient data is only ever permitted in production on Lorraine's Mac.

Part 1 · Setup

01Prerequisites

Confirm all of these before running any scenario.

Environment

  • Backend running at your local URL (e.g. http://localhost:8000 — adjust BASE_URL in the seed script)
  • Frontend served and reachable in a browser
  • SQLite database initialised (alembic upgrade head or equivalent)
  • At least one staff login created (used by the seed script for session auth)
  • Diagnosis settings files present for: Low Back Pain – Left, Dorsalgia – Right, Pain in Hip – Left (minimum for seed scenarios)

Tools needed

  • Python 3.10+ with httpx installed (pip install httpx)
  • Access to the repo to run scripts/seed_test_data.py
  • A browser for manual UI verification of generated PDFs
  • Optional: sqlite3 CLI to inspect the database directly
Do not point the seed script at the production Mac. The seed script is for the local dev environment only. All records it creates carry a test_seed=true flag so they can be wiped cleanly.

02Seed script — Claude Code prompt

Drop this prompt into Claude Code at the root of the repo. It will read your API routes and generate scripts/seed_test_data.py and scripts/reset_test_data.py.

Claude Code prompt

I need a test data seed script for the DeYoe Wellness Acupuncture packet tool.

Before writing anything, read the API route definitions and the database schema
(models/tables) so the script calls real endpoints with the correct payloads.

Create two scripts:
1. scripts/seed_test_data.py  — populates all the scenarios below
2. scripts/reset_test_data.py — wipes only the seeded records so we can run clean

Use only fictional patients (Jane Doe / John Doe style). No real names, DOBs,
VA numbers or SSN digits anywhere — HIPAA applies even in dev. Use the existing
fixture VA numbers and names already in the codebase (e.g. VA0011223344,
Jane Doe 1234) wherever they exist.

Call the FastAPI endpoints in sequence (use httpx), not the database directly —
we want the business logic and triggers to fire as they would in real use.
Tag every created record with test_seed=true (or a notes/label field if that
doesn't exist) so reset_test_data.py can remove them without touching real data.

Part 2 · Scenarios

03Patient & authorization scenarios

Covers patient creation, authorization entry and the visit-limit and date-period guards.

P-01 New patient, first authorization Positive Seed: S1

A brand-new patient with no prior history. Confirms the patient and authorization are created correctly and the dashboard tile appears.

  1. Open S6 (New authorization). Enter: Jane Doe, DOB 1960-03-15, last four 1234, title Ms., pronoun her.
  2. Diagnosis: Low Back Pain – Left. Approved visits: 8. Period: 2026-09-01 → 2026-11-30. VA number: VA0011223344. Facility: Atlanta VAMC.
  3. Save. Check S2 (dashboard) — Jane Doe tile shows 0 of 8 visits.
✓ Authorization saved · patient record created · tile on dashboard
P-02 Same patient, second authorization, same diagnosis Positive Seed: S2

Jane Doe returns with a new VA authorization for the same diagnosis. Visit 1 of the new auth should pre-fill answers from her last visit under this diagnosis in S1.

  1. Find Jane Doe on S2. Create a second authorization: Low Back Pain – Left, 6 visits, period 2026-12-01 → 2027-02-28, new VA number.
  2. Add visit 1 on S9. Open the answer panel.
  3. Confirm pre-fill source shows previous_authorization for the carried-over answers.
✓ Answers pre-filled from last visit of previous authorization · answer_source = previous_authorization
P-03 Same patient, different diagnosis — answers reset Positive Seed: S3

Jane Doe starts a new authorization with a different diagnosis. Visit 1 answers must come from the new diagnosis's defaults, not from her Low Back Pain history.

  1. Create a third authorization for Jane Doe: diagnosis Dorsalgia – Right, 6 visits.
  2. Add visit 1. Open the answer panel.
  3. Confirm answers match the Dorsalgia – Right defaults from its settings file, not Low Back Pain values.
  4. Confirm answer_source = default for all answers.
✓ Answers reset to Dorsalgia – Right defaults · no carry-over from Low Back Pain
P-04 Authorization at visit limit — add visit blocked Negative Seed: S4

John Doe's authorization has 4 visits approved and all 4 recorded. Adding a 5th visit must be blocked at every layer.

  1. Open John Doe's authorization (S7). Confirm visit count shows 4 of 4.
  2. Attempt to add a 5th visit via S9's "Add visit" button — it should be disabled with a clear reason shown.
  3. Try a direct POST /visits API call with this authorization ID. Expect a 409 response.
  4. Confirm the SQLite trigger also blocks a direct DB insert (check logs).
✗ UI button disabled · API returns 409 · DB trigger fires
P-05 Duplicate patient detection Boundary

A second patient with the same last name, DOB, and last four as Jane Doe is entered. The system should warn but not block.

  1. On S6, enter a new patient: last name Doe, DOB 1960-03-15, last four 1234, first name Joan.
  2. Confirm a duplicate warning is surfaced (suggested match shown).
  3. Confirm the system does not merge automatically — Joan Doe can still be saved as a separate patient.
⚠ Duplicate warning shown · not merged automatically · can be saved

04Visit tracking scenarios

Covers date validation, answer pre-fill carry-forward, manual edits, and the final visit rule.

V-01 Consecutive visits — answers carry forward Positive Seed: S6

Visits 2–5 on Jane Doe's S1 authorization. Each visit's answers should pre-fill from the immediately preceding visit.

  1. Open visit 2 on S9. Confirm all answers match visit 1 exactly. answer_source = previous_visit for all.
  2. Change one answer on visit 2 (e.g. uncheck an activity). Save.
  3. Open visit 3. Confirm it reflects visit 2's changed state. The unchecked activity should still be unchecked. answer_source for that field = previous_visit.
  4. Confirm pain level is not pre-selected on any visit — it shows the previous value as a hint only.
✓ Answers carry forward visit-by-visit · pain level hint shown but not pre-selected · answer_source correct
V-02 Edit on visit 3 carries forward to visits 4+ Positive Seed: S6

An answer changed on visit 3 should propagate to all later unsent visits. Sent visits must not change.

  1. On visit 3 (unsent), uncheck an activity that was previously checked.
  2. Open visit 4. Confirm the unchecked state carried over. answer_source = previous_visit.
  3. If visit 1 or 2 were already sent, confirm they are unchanged.
✓ Edit carries forward to unsent visits · sent visits untouched
V-03 Visit date outside authorization period — blocked Negative Seed: S5

John Smith's authorization runs 2026-10-01 to 2026-10-31. A visit dated November 1 must be blocked.

  1. Open John Smith's authorization. Try to add a visit with date 2026-11-01.
  2. Confirm the UI shows a clear error: date is outside the authorization period.
  3. Try a direct POST /visits with the same date. Expect a 409 or 422.
  4. Try a date of 2026-09-30 (one day before the period starts). Same result expected.
✗ UI error shown · API blocks with 409/422 · dates outside period rejected
V-04 Visit date on first and last day of period — allowed Boundary Seed: S5

Confirm the authorization period boundary is inclusive on both ends.

  1. Add a visit to John Smith's authorization with date 2026-10-01 (period start). Should succeed.
  2. Add a second visit with date 2026-10-31 (period end). Should succeed.
✓ Both boundary dates accepted
V-05 Final visit — last-page rules applied Positive Seed: S7

John Doe's 4th visit is marked is_final=true. The generated page must carry the last-visit label, closing note, and Excellent ticked.

  1. On John Doe auth S4, open visit 4 on S9. Mark it as final.
  2. Generate the packet (S11 → S12). Open the last page of the notes PDF.
  3. Confirm: label "Last Visit in authorization" present; closing note present; Excellent ticked under Today's response.
  4. Attempt to add a visit 5 — it must be blocked (final visit already set + limit reached).
✓ Last-page rules on visit 4 · no visit after final
V-06 Warning at 2 visits remaining Boundary Seed: S1 (6 of 8 visits recorded)

At 6 of 8 visits recorded the dashboard and S7 must show a "2 visits remaining" warning.

  1. Ensure Jane Doe auth S1 has exactly 6 visits recorded.
  2. Check S2 (dashboard tile) — warning badge should appear.
  3. Open S7 (authorization detail) — warning message visible.
⚠ Warning shown on dashboard and S7 at 2 visits left

05Packet generation scenarios

Covers the 8-visit and 12-visit acceptance criteria, per-page edits, and the three-file structure.

G-01 8-visit completed packet — acceptance criterion Positive Seed: S4 (John Doe, 4 visits) — or use a fresh 8-visit auth

One of the two formal acceptance criteria. A completed 8-visit authorization must produce a correctly structured packet.

  1. Ensure an authorization with exactly 8 visits recorded and visit 8 marked is_final.
  2. Build packet on S11. Select cover sheet: Atlanta VAMC Request for Services. Include RFS if diagnosis ICD-10 is confirmed.
  3. Open the notes PDF (S12). Check every page:
PageMust have
1 (Visit 1)"INITIAL VISIT IN AUTHORIZATION" label · first-visit physician note · patient name, VA number, last four, date (top = bottom)
2–7 (Visits 2–7)Only date, pain level and patient answers differ · name/VA number/last four repeat · post-treatment always 1/10
8 (Visit 8)"Last Visit in authorization" label · closing note · Excellent ticked · date (top = bottom)
✓ All 8 pages correct · top and bottom dates match on every page · correct labels on first and last
G-02 12-visit completed packet — acceptance criterion Positive Seed: S10

Second formal acceptance criterion. Same structure as G-01 but 12 pages.

  1. Use Jane Smith's 12-visit authorization (seed S10). All 12 visits recorded; visit 12 is_final.
  2. Build and open the packet. Verify pages 1, 2–11 (middle), and 12 follow the same rules as G-01.
  3. Count: cover sheet (1) + RFS (2, if included) + notes (12) = total pages. Confirm the cover sheet's page count field matches.
✓ 12 pages correct · cover sheet page count accurate
G-03 Per-page edit — change appears in output Positive Seed: S9

A single page can be edited after packet generation and the change must appear in the merged PDF.

  1. On John Doe's packet (S12), open the per-page editor for visit 2. Change the displayed pain level to 7 (page override only — do not change the visit record).
  2. Confirm S12 shows "edited since generated" indicator.
  3. Regenerate / refresh the PDF. Open page 2. Pain level must read 7.
  4. Confirm the edit is logged in S20 (activity log) with before/after values.
  5. Confirm the consistency check panel flags the mismatch between the stored visit value and the page override.
✓ Edited value on page 2 · logged in activity log · mismatch flag shown
G-04 Cover sheet page count matches actual files Positive

The cover sheet's total page count field must equal 1 (cover) + notes pages + RFS pages (if included).

  1. Generate a packet: 8 notes + RFS (2 pages) + cover sheet = 11 pages total.
  2. Open the cover sheet PDF. Confirm the page count field reads 11.
  3. Repeat without RFS: 8 notes + cover = 9 pages. Confirm cover reads 9.
✓ Page count on cover sheet matches actual file total in both cases
G-05 Three separate PDF files — not merged Positive

The output must be three separate files (client decision). A single merged PDF would be rejected by the VA.

  1. After building a packet with cover + RFS + notes, go to S12 download area.
  2. Confirm three separate download links: cover sheet, clinical notes, RFS.
  3. Download each. Confirm they are three distinct PDF files, not one merged file.
✓ Three separate PDFs available for download

06Fax flow scenarios

Covers the review → confirm → send → status flow. Use the test fax destination Lorraine provides — 404-738-1714 is the practice's own sending number, not a test destination.

Before running fax scenarios: confirm SRFax API credentials are entered in S19 (settings). Use a test destination number Lorraine has confirmed — never the practice's own fax number.
F-01 Fax flow blocked until approved Negative Seed: S11

The send screen (S13) must not be reachable until the packet is in approved state.

  1. Take a packet in draft state. Try navigating directly to its S13 URL.
  2. Confirm the app redirects away or shows a clear block — it must not show "Sent · Delivery confirmed".
  3. Try the same with a packet in ready state (built but not approved).
✗ S13 and S14 unreachable until packet is approved · no skip-ahead via direct URL
F-02 Confirm screen shows destinations and sending number Positive Seed: S11

S13 must show each destination fax number and the sending number before the user confirms.

  1. Approve John Doe's packet (S11 seed). Proceed to S13.
  2. Confirm S13 shows: destination number, sending number 404-738-1714, and a summary of each file being sent.
  3. Do not confirm yet — just verify the display.
✓ Destination + sending number visible · file list shown before confirm
F-03 Blairsville send also goes to Atlanta automatically Positive

Any authorization with facility Blairsville VA must automatically add Atlanta VAMC as a second destination.

  1. Create an authorization with facility Blairsville VA. Build and approve a packet.
  2. On S13, confirm two destination rows: Blairsville VA (primary) and Atlanta VAMC (automatic copy).
  3. Confirm the Atlanta copy uses the Atlanta VAMC Request for Services cover sheet.
✓ Two destinations on S13 · correct cover sheet for Atlanta copy
F-04 Failed send shows clearly and can be retried Negative

Simulate a fax failure (disconnect SRFax credentials or use an invalid destination). The failure must be clear and retryable.

  1. Temporarily set an invalid SRFax API key in S19.
  2. Attempt to send a packet. Confirm S14 / S15 shows a clear failure state — not "Sent" or blank.
  3. Restore the correct API key. Use the retry action. Confirm a new transmission attempt is logged.
  4. Confirm the failed attempt is also logged in the fax log (S20) with status failed.
✗ Failure shown clearly · retry creates new attempt · both logged
F-05 Sent packet is read-only Negative

Once a packet moves to sent state the authorization must become read-only. No edits, no new visits, no re-build.

  1. After a successful send, return to the authorization (S7).
  2. Confirm: Edit authorization button is disabled or hidden; "Add visit" is disabled; "Build packet" is disabled.
  3. Try direct API calls to edit the authorization or add a visit. Expect rejection.
  4. Confirm a correction flow (new packet linked to the old) is the only path forward.
✗ All edit actions disabled on sent authorization · correction flow available

08Reset procedure

Run this to wipe seeded test data and return to a clean state. It removes only records tagged test_seed=true.

python scripts/reset_test_data.py --base-url http://localhost:8000

The script will print a confirmation of each record deleted. If you need a full database wipe (e.g. after a schema change), delete the SQLite file and re-run migrations, then re-seed.

Never run reset_test_data.py against the production Mac. The reset script has a guard that refuses to run if BASE_URL is not localhost, but confirm visually before running.
