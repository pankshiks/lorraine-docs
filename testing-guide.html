Testing guide

End-to-end test scenarios covering the full patient journey: authorization, visit tracking, packet generation and fax. Includes the seed and reset scripts and how to run them. Use fake data only.

Version 1.2 · 6 Oct 2026 — template builder added Internal not for the client HIPAA fake data only — never real names, VA numbers or DOBs
01Prerequisites 02Seed & reset scripts 03Patient & authorization 04Visit tracking 05Packet generation 06Fax flow 07Template builder 08Negative / blocked cases 09Reset procedure 10Fixture reference
How to read the scenarios. Each scenario has a Positive (should succeed), Negative (should be blocked), or Boundary (edge / limit) badge. Expected outcomes are shown at the bottom of each card. Run positive cases first to confirm the happy path, then negative cases to confirm guards hold. Seed N refers to the scenarios loaded by seed_test_data.py (section 02); dates are counted from the day you seed.
HIPAA reminder. Use only fictional patients (Jane Doe, John Doe, and the seed's Joan B Doe). No real names, dates of birth, VA authorization numbers, or SSN digits anywhere — in the database, logs, screenshots, or commit messages. Real patient data is only ever permitted in production on Lorraine's Mac.

Part 1 · Setup

01Prerequisites

Confirm all of these before running any scenario.

Environment

  • The app running locally: docker compose up --build (API http://localhost:8000, app http://localhost:8080) or make dev
  • Database migrated (the container does it on start; locally make migrate) and the demo clinic loaded — Jane Doe and John Doe from fixtures/
  • ENVIRONMENT=development — the seed signs in with the demo sign-in (or pass --email / --password)
  • All 20 diagnosis templates are set up; every ICD-10 code is confirmed (decision 28 Sep), so the RFS can be included for any diagnosis
  • Fax: leave FAX_MODE=fake (the default) — every step runs, nothing is dialled, faxes show “Demo — not faxed”. For the failure case (F-04) add FAX_FAKE_FAIL_NUMBERS=["706-555-0199"].

Tools needed

  • The backend's Python environment (it already has httpx)
  • backend/scripts/seed_test_data.py and reset_test_data.py; scenarios in fixtures/test_seed.json
  • A browser for the screens and the generated PDFs
  • Optional: sqlite3 to look at the database (never needed to run the tests)
Development only. Never seed or reset the production Mac — the reset refuses to run with ENVIRONMENT=production. There is no test_seed flag on records: the seed uses its own VA numbers (VA0090000001–VA0090000099, reserved for testing) and creates one patient, Joan B Doe; that is how the reset finds exactly what it added.

Part 2 · Scenarios

03Patient & authorization scenarios

Covers patient creation and correction, authorization entry, and the visit-limit and date-period guards.

P-01 New patient, first authorization Positive Seed 1 — or by hand

A brand-new patient with no prior history. Confirms the patient and authorization are created correctly and appear on the dashboard.

  1. Patients › + Add patient: a made-up patient, e.g. Jake Doe, DOB 1972-02-12, last four 2222, Mr. / his. Save — it opens New authorization for him.
  2. Diagnosis: Pain in Knee – Left. VA number: an unused one (VA00 + 8 digits, e.g. VA0090000060). Facility Atlanta VAMC, office Clarkesville, approved visits 6, period today → +60 days.
  3. Create. S7 shows 0 of 6 approved; the authorization is on the dashboard (S2) and the patient list.
  4. A period may also lie in the past (client, 2 Oct) — e.g. 05/04/2026 → 07/03/2026 for an authorization that already ended. Each VA number is used once — VA0011223344 is Jane's earlier authorization.
✓ Patient saved · authorization saved · 0 of 6 on S7 · listed on the dashboard
P-02 Same patient, second authorization, same diagnosis Positive Seed 2

Jane Doe returns with a new VA authorization for the same diagnosis. Visit 1 of the new authorization pre-fills from her last Low Back Pain – Left visit.

  1. Open seed 2 (Jane Doe · Low Back Pain – Left · 0 of 8) and click + Add visit.
  2. The visit screen says “Continued from the last Low Back Pain – Left authorization (VA0012345678, …)” and the answers match her last visit there.
  3. Enter a date and a pain level, save (nothing to sign — the signature is pre-printed). The visit's answers are recorded with source previous_authorization.
✓ Answers pre-filled from her previous authorization · answer_source = previous_authorization
P-03 Same patient, different diagnosis — answers reset Positive Seed 3

Jane Doe starts an authorization for a diagnosis she has never had. Visit 1 answers come from that diagnosis's defaults, not her Low Back Pain history.

  1. Open seed 3 (Jane Doe · Pain in Shoulder – Right · 0 of 6) and click + Add visit.
  2. The screen says “Started from the Pain in Shoulder – Right template's default ticks”; the answers match that template's defaults.
  3. Save visit 1: source default.
✓ Answers start from Pain in Shoulder – Right defaults · no carry-over from Low Back Pain
P-04 Authorization at visit limit — add visit blocked Negative Seed 4

John Doe's Dorsalgia – Left authorization has 4 visits approved and all 4 recorded. A 5th visit is blocked at every layer.

  1. Open seed 4 on S7: 4 of 4 approved, “All 4 approved visits are recorded”, + Add visit disabled.
  2. Open the visit screen directly (…/visits/new): “All approved visits recorded”, no form.
  3. API: POST /api/authorizations/{id}/visits → 422 (“Visit 4 was the final visit — no visits can follow it”).
  4. Database: a direct insert is refused by the visit triggers.
✗ Button disabled · visit screen blocked · API 422 · database trigger refuses
P-05 Duplicate patient detection Boundary By hand

A new patient with the same last name, date of birth and last four as Jane Doe. The app warns and never merges.

  1. Add patient: first name Joan, last name Doe, DOB 1961-03-14, last four 1234 (Jane Doe's).
  2. As soon as the details match, a warning appears: “Possible duplicate: Jane Doe … already exists. Nothing is merged automatically”, with View that patient. Save patient stays disabled.
  3. Tick “This is a different person — create a new patient anyway” — saves as a separate patient.
⚠ Duplicate warning · never merged · saved only once confirmed as a different person
P-06 Correct a saved patient's details Positive By hand

A typo in a saved patient is corrected on Edit patient. Same checks as adding; packets already sent keep the details they went with.

  1. Open a patient (e.g. Jake Doe from P-01) › Edit patient: the saved details are filled in.
  2. Change the middle initial; click Cancel — “Leave without saving?” asks first. Stay.
  3. Type another patient's last name, DOB and last four: the duplicate warning appears and Save is disabled. Put them back.
  4. Save changes → back on the patient; the change is in the activity log (S20) with before and after.
✓ Saved details shown · same checks · duplicate caught · saved and logged

04Visit tracking scenarios

Covers answer carry-forward, corrections, date validation, the final visit and the visits-left warning.

V-01 Consecutive visits — answers carry forward Positive Seed 6

On John Doe's Pain in Shoulder – Left (5 of 8, pain 3 · 4 · 3 · 5 · 4), each visit's answers start from the visit before.

  1. On S7, visits 2, 3 and 5 show “same as last visit”; visit 4 shows changed (its Type of pain differs).
  2. Click + Add visit: the answers match visit 5; the pain level is not pre-selected — “Last visit: 4 — a hint only”.
✓ Answers carry forward · “changed” marked · pain level a hint only
V-02 Edit on visit 3 carries forward to visits 4+ Positive Seed 6 · Seed 12

Correcting an answer on visit 3 carries to the later visits that kept it unchanged. Sent visits can't be edited.

  1. On seed 6, click Edit → on visit 3, untick a painful activity, Save changes.
  2. Visits 4 and 5 lose that activity too; visit 4 keeps its own Type of pain change.
  3. On seed 12 (packet approved) there are no Edit links; PUT …/visits/{id} → 409 “sent packets are never edited”.
✓ Edit carries forward to unsent visits · sent visits locked
V-03 Visit date outside authorization period — blocked Negative Seed 5

Seed 5's period runs from the day you seeded to 30 days later. Dates outside it are refused.

  1. On seed 5, Add visit with the date period end + 1 day: “Outside the authorization period (…)” shows on the date box.
  2. API: the same date → 422.
  3. A date before the previous visit is refused too: “Must be after the previous visit (…)”.
✗ Error on the date box · API 422 · dates outside the period refused
V-04 Visit date on first and last day of period — allowed Boundary Seed 5

The period is inclusive at both ends.

  1. Seed 5's visit 1 is on the period start date — accepted.
  2. Add a visit dated exactly on the period end — accepted.
✓ Both boundary dates accepted
V-05 Final visit — last-page rules Positive Seed 7

The final visit's page carries the last-visit label, the closing note and Excellent ticked; nothing can follow it.

  1. Build seed 7's packet (S11 → S12). On the last notes page: “Last Visit in authorization”, the closing note (“Pt responded well to tx. Pt had an excellent outcome w/ acupuncture”), Excellent ticked under Today's response.
  2. S7: Add visit is disabled.
  3. Ending early: mark an earlier visit final (Edit visit › “Mark as final visit”). S7 then says “Visit N is marked final — treatment ended, so no more visits can follow it”, Add visit is disabled, and the visit screen shows “Treatment ended — no more visits”.
✓ Last-page rules on the final visit · no visit after final, explained up front
V-06 Warning at 2 visits remaining Boundary Seed 6

With 2 approved visits left, S7 and the dashboard warn.

  1. Record visit 6 on seed 6 (6 of 8).
  2. S7 shows “2 approved visits left on this authorization”.
  3. The dashboard's Nearing last visit tile and Needs attention list include it.
⚠ Warning on S7 and the dashboard at 2 visits left
V-07 A half-entered visit isn't lost by accident Boundary Any authorization

Leaving the visit screen with something entered asks first.

  1. Start a visit (e.g. pick a pain level), then click a sidebar link, Cancel or Back: “Leave without saving?” — Stay and keep editing keeps what you typed.
  2. Refresh or close the tab: the browser's own “Leave site?” prompt.
  3. Nothing entered, or just saved: no question.
⚠ Asks before discarding · never after saving

Covers the 8-visit and 12-visit acceptance criteria, per-page edits, the cover page count and the three-file structure.

G-01 8-visit completed packet — acceptance criterion Positive Seed 9

One of the two formal acceptance criteria. A completed 8-visit authorization produces a correctly structured packet.

  1. Seed 9 (John Doe · Pain in Knee – Right · 8 of 8, visit 8 final).
  2. Build packet (S11): cover Atlanta VAMC — Request for Services, tick Include RFS — box 21 carries Dr. DeYoe's pre-printed signature (page 2 is faxed blank — nothing to sign there). On Preview the RFS is the VA's own form: the values sit inside its boxes, the chosen radios in boxes 6, 10, 11 and 12 are filled, and box 11's answer (YES) is circled.
  3. Open the notes on Preview (S12) and check every page:

G-02 12-visit completed packet — acceptance criterion Positive Seed 10

Second formal acceptance criterion. Same structure as G-01 with 12 pages.

  1. Seed 10 (Jane Doe · Low Back Pain – Right · 12 of 12, visit 12 final). Build with the RFS.
  2. Pages 1, 2–11 and 12 follow the G-01 rules.
  3. The cover sheet's page total reads 15 (cover 1 + notes 12 + RFS 2).
✓ 12 pages correct · cover page count 15
G-03 Per-page edit — appears in the output and blocks sending Positive Seed 11

A single notes page can carry its own name, VA number or last four (S12 “Edit this page”). It is flagged everywhere and the packet can't be sent until it is undone. A page edit can't change the pain level — that is corrected on the visit itself (Edit visit).

  1. Seed 11's notes page 3 was edited to the name “Jon Doe”: the notes PDF page 3 shows it; the other pages show John Doe.
  2. Preview flags it: “Name, VA number or last four don't match across the files — Clinical notes page 3: …”, and the page shows “Edited since generated”.
  3. Review & send: Confirm and send is disabled; the API refuses approval (422) — “undo the page edits first”.
  4. The edit is in the activity log (S20). Seed 11's visit 3 pain was corrected 5 → 6 through Edit visit — all pages follow it.
  5. Undo edit on page 3 clears the warning.
✓ Edited value on its page · flagged on Preview and S13 · sending blocked until undone · logged
G-04 Cover sheet page count matches actual files Positive Seed 9

The cover sheet's total = 1 (cover) + notes pages + RFS pages (if included).

  1. Seed 9 with the RFS: the cover reads 11 (1 + 8 + 2).
  2. Rebuild without the RFS: the cover reads 9.
✓ Page count on the cover matches in both cases
G-05 Three separate PDF files — not merged Positive Seed 9 · Seed 12

The output is always three separate files (client decision) — a merged PDF is rejected by the VA.

  1. Preview (S12): three tabs — Cover sheet, Clinical notes, RFS — and Download all 3 files; each download is logged.
  2. Seed 12 (approved): the fax log's Cover · Notes · RFS links open three distinct PDFs (1, 3 and 2 pages), exactly as sent.
✓ Three separate PDFs, downloadable and kept as sent

06Fax flow scenarios

Covers review → confirm → send → status. Demo mode (FAX_MODE=fake) runs every step without dialling. For real SRFax, only the numbers in FAX_ALLOWED_NUMBERS are dialled before go-live — 404-738-1714 is the practice's own sending number, never a destination.

F-01 Nothing is sent, or shown as sent, before confirming Negative Seed 9 · Seed 12b

Review & send (S13) is the confirmation: “Confirm and send” approves the packet and hands its faxes to the sender. There is no separate “approved” step before it.

  1. Open S13 for a draft (seed 12b): it shows what will be sent and offers Confirm and send — Cancel in its dialog sends nothing (still a draft).
  2. Open Send result (S14) for a packet not yet confirmed (seed 9): “This packet hasn't been approved yet — nothing has been sent”.
  3. After confirming, a fax shows Queued until the service reports it — never “Sent” before that.
✗ Nothing sent without Confirm and send · Queued never shown as Sent
F-02 Confirm screen shows destinations, sending number and files Positive Seed 12b

S13 shows each destination, the sending number and the files before the confirmation.

  1. Open seed 12b's Review & send — also straight from a bookmark or typed link: it shows the saved packet.
  2. Check: Blairsville VA 404-417-1581 and Atlanta VAMC 404-639-9335 (automatic copy), sending from 404-738-1714, and the cover, notes and RFS file names with page counts.
  3. Don't confirm yet.
✓ Destinations + sending number + files shown before confirming
F-03 Blairsville send also goes to Atlanta automatically Positive Seed 12b

A Blairsville VA packet always adds Atlanta VAMC as a second destination.

  1. On seed 12b, Confirm and send → Send 2 faxes.
  2. Send result (S14) lists two faxes — Blairsville VA and the automatic Atlanta copy (Atlanta “Request for Services” cover) — Queued, then Sent (demo: “Demo — not faxed”).
✓ Two destinations · correct cover for the Atlanta copy · each tracked
F-04 Failed send shows clearly and can be retried Negative Any packet · test fax

A failure is shown with its reason and retried as a new attempt; every attempt is kept.

  1. Demo mode: start the backend with FAX_FAKE_FAIL_NUMBERS=["706-555-0199"]; on Practice & sending send a test fax to 706-555-0199 (or set a VA facility's fax to it for a packet — and set it back after).
  2. The fax log (S15) shows Failed with the reason (“No answer (demo failure)”). With real SRFax: e.g. “SRFax refused it: …”.
  3. Retry (S14 or S15) adds attempt 2 of 2; attempt 1 stays as it was. Each step is in the activity log (S20).
✗ Failure shown with its reason · retry = new attempt · all attempts kept and logged
F-05 Sent packet is read-only Negative Seed 12

Once a packet is approved its contents are frozen: the visits can't be edited and the files as sent never change.

  1. Seed 12's S7: no Edit links on the visits; PUT …/visits/{id} → 409 “sent packets are never edited”.
  2. The files as sent (fax log links) stay exactly as approved.
  3. Today the authorization itself can still be corrected (Edit authorization — the VA no longer extends authorizations, client 2 Oct) and a new packet built — the linked correct-and-re-send packet (S21) isn't built yet (QA M3).
✗ Visits locked · files as sent unchanged · correction flow still to come (M3)

09Reset procedure

Removes what the seed added — and nothing else — so the scenarios can be seeded again.

cd backend
python scripts/reset_test_data.py          # lists what it would remove
python scripts/reset_test_data.py --yes    # removes it
docker compose exec backend python scripts/reset_test_data.py --yes   # inside Docker

It removes every authorization with a seed VA number (VA0090000001–099) — with its visits, packets, page edits, fax records and stored PDFs, including anything a tester added to them — and Joan B Doe (kept, with a warning, if she has been given another authorization). Jane Doe and John Doe themselves, every other patient and the activity log are never touched (the log can't be changed). It works on the database directly because the app has no hard delete by design. For a full wipe (e.g. after a schema change), delete the SQLite file, restart (migrations and the demo clinic load on start), then re-seed.

Never run reset_test_data.py against the production Mac. It refuses to run with ENVIRONMENT=production and deletes only with --yes — check what it lists first.
